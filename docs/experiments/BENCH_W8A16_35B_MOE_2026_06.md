# W8A16 (GPTQ-8bit) 35B-A3B MoE — capacity + compile A/B (gfx908/MI100, 2026-06)

Closes the missing **W8A16 weight-only** data point called out in
`RESEARCH_FP16_OPTS_AND_QUANT_FIT.md` §3 and the compile-series caveats
(`BENCH_FP16_COMPILE_MOE_2026_06.md`, `BENCH_FP16_COMPILE_QUANT_MOE_2026_06.md`):
an 8-bit weight-only MoE that keeps the FP16 MFMA compute path (int8→fp16
dequant) while halving weight bytes, stacked with the gfx908 torch.compile win.

Two workstreams landed together:

1. **WS1 — torch.compile launch scripts** (`scripts/launch_compile_*.sh`):
   ship the concurrency-gated compile win as standalone, gated launch scripts
   (no change to rocm.py defaults).
2. **WS2 — W8A16 35B capacity validation** (this model): download, load/serve,
   quality gates, compile A/B, capacity.

> **Session note (thermal):** to spare GPU 0 from a thermal hot-spot, the runs
> in this doc were executed at **TP=2 pinned to GPUs 1,2**
> (`HIP_VISIBLE_DEVICES=1,2 LAUNCH_TP=2`). The shipped launch scripts target
> **TP=4**; the TP=2 figures here are a same-hardware A/B (both arms TP=2), so
> the **compile Δ is valid**, but absolute tok/s and the fp16-vs-W8A16 PPL Δ
> (fp16 35B needs TP=4 to fit) are deferred to a TP=4 re-run.

## Capacity — the axis W8A16 is actually for

| Config | GPUs | Weights/GPU | GPU KV cache | Max concurrency @ 16k |
|---|---|---:|---:|---:|
| **W8A16 35B-A3B (this)** | **2** (TP=2, 0.90) | 18.36 GiB | **626,315 tok** | 38.23× |
| fp16 35B-A3B (compile MoE doc) | 4 (TP=4, 0.92) | ~16.3 GiB | 896,691 tok | 54.7× |

**The headline capacity result:** the 8-bit MoE **fits and serves on 2 MI100s**
(half the hardware) with a 626k-token KV cache. The fp16 35B (~67 GiB) does not
fit at TP=2 — it requires all 4 GPUs to load at all. W8A16 therefore either
(a) frees 2 GPUs for a second model / second replica, or (b) at TP=4 leaves far
more VRAM for KV/context than fp16 (TP=4 re-run will quantify the KV headroom).

## torch.compile A/B (TP=2, GPUs 1,2; **same v0.22.1 binary both arms**)

`mode=3` + `FULL_AND_PIECEWISE` (compile) vs `FULL_DECODE_ONLY` (baseline),
synthetic random 1024/256, 200 prompts, seed 42, max-concurrency = cell, both
arms on the rebuilt `happy-carrots` v0.22.1rc1 worktree (see rebuild note below).

| cell | baseline (FULL_DECODE_ONLY) tok/s | compile (mode3+FULL_AND_PIECEWISE) tok/s | **Δ** |
|---|---:|---:|---:|
| tp2_c1 | 55.12 | **62.97** | **+14.2 %** |
| tp2_c2 | 74.47 | **104.54** | **+40.4 %** |
| tp2_c4 | 115.27 | **170.70** | **+48.1 %** |

p50 latencies (compile): c1 TTFT 135.2 ms / TPOT 15.32 ms; c2 197.0 / 18.34;
c4 256.5 / 22.56. Baseline: c1 148.6 / 17.63; c2 245.0 / 26.01; c4 302.8 / 33.40
— compile improves **both** throughput and latency at every concurrency.

> **Result: monotonic compile win that grows with concurrency, and — unlike the
> 0.20.2 dense runs — c1 is now positive (+14 %).** The earlier 0.20.2 compile
> arm (c1=63.54, c2=106.40) is superseded by this same-binary v0.22.1 A/B; the
> absolute tok/s are close, but only the v0.22.1 numbers have a matched baseline.

> **Why we rebuilt.** Mid-session the emdash framework recreated the compiled
> `fuzzy-hornets` 0.20.2 worktree (its `vllm/_C.abi3.so` was removed), leaving
> only an older `0.18.1` tree that is **incompatible with torch.compile here**
> (its compiled `_C` is missing `silu_and_mul_per_block_quant`, which the v0.22
> Inductor `act_quant_fusion` pass imports at init — the `AttributeError` was a
> stale-binary symptom, *not* a torch.compile defect). A valid A/B requires
> *both* arms on the same binary, so we **rebuilt the current worktree**
> (`happy-carrots`, v0.22.1rc1) in-place for gfx908:
>
> ```bash
> # As executed (pinned env Python). Per AGENTS.md the standard wrapper is `uv`:
> #   PYTORCH_ROCM_ARCH=gfx908 MAX_JOBS=56 VLLM_TARGET_DEVICE=rocm \
> #     uv run python setup.py build_ext --inplace
> PYTORCH_ROCM_ARCH=gfx908 MAX_JOBS=56 VLLM_TARGET_DEVICE=rocm \
>   /opt/vllm-env/bin/python3 setup.py build_ext --inplace   # ~6 min, rc=0
> ```
>
> The new build has `silu_and_mul_per_block_quant`; both the baseline
> (KV 677,701 tok, 41.36× @ 16k) and compile (KV 603,973 tok, 36.86× — Inductor's
> higher peak memory, as documented in rocm.py) arms serve cleanly on it.

Compile warmup on v0.22.1: ~30 s load + 7.7 s Dynamo bytecode transform +
38.7 s Inductor graph compile + cudagraph capture (one-time, cached at
`/root/.cache/vllm/torch_compile_cache`). The Dynamo guard
(`fused_silu_quant_int8.py` `torch.compiler.is_compiling()`, commit `24ac8f64e`)
held on this W8A16 MoE — third distinct model family confirmed (dense 9B, fp16
35B, now W8A16 35B).

### MoE config caveat (affects both arms equally)

vLLM logged:
> `Using default MoE config. Performance might be sub-optimal! Config file not
> found at .../E=256,N=256,device_name=AMD_Instinct_MI100,dtype=int8_w8a16.json`

At bench time there was **no gfx908-tuned fused-MoE config** for this
`int8_w8a16` E=256/N=256 shape, so absolute throughput is understated. This hits
**baseline and compile equally**, so the compile Δ is valid.

**Follow-up done** (`BENCH_MOE_TUNE_W8A16_E256N256_2026_06.md`): we tuned this
exact shape from scratch on the v0.22.1 stack. It is a **concurrency-gated win**
— +15 % c2 / +24 % c4 but −11.6 % c1 (the tuned decode-M tile loses single-stream
to the Triton default). Shipped opt-in via `LAUNCH_TUNED_MOE=1`
(`VLLM_TUNED_CONFIG_FOLDER` → `scripts/moe_configs_w8a16/`), **not** installed
globally so it can't regress c=1. Unlike the inherited int4 configs (−38 %
server regression) and the int4/N=128 retune (no headroom), this N=256 shape has
real, prefill-safe tuning headroom.

## WS1 — compile launch scripts shipped

`scripts/_compile_cell_common.sh` (shared) + per-cell wrappers, all TP=4,
`VLLM_MI100_TORCH_COMPILE=1` + `VLLM_MI100_ALLOW_PIECEWISE=1` +
`--compilation-config '{"mode":3,"cudagraph_mode":"FULL_AND_PIECEWISE"}'`,
gpu-mem-util 0.90, ±5 % gate vs the recorded compile-arm reference:

- `launch_compile_fp16_tp4_c{1,2,4}.sh` — dense FP16 9B (refs from `..PORT_0202..`)
- `launch_compile_moe_tp4_c{1,2,4}.sh` — fp16 35B-A3B (refs from `..COMPILE_MOE..`)
- `launch_compile_qmoe_tp4_c{1,2,4}.sh` — W4A16 512e MoE (refs from `..QUANT_MOE..`)
- `launch_w8a16_moe_tp4_c{1,2,4}.sh` — this W8A16 35B (compile baked in)

TP=1 deliberately not shipped (compile regresses there on 0.20.2). An ad-hoc
`LAUNCH_TP=` override exists for thermal-subset testing (disables the ±5 % gate
since references are TP=4). A compiled worktree is pinned via `VLLM_SRC` because
the editable `.pth` can point at an uncompiled checkout (PERF_GFX908.md §3).
